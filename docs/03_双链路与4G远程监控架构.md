# 灵云01号 双链路与4G远程监控架构

> 本方案在既有**串口数传链路**基础上，新增**4G 公网监控链路**，实现设备异地远程监控。
> 当前阶段：**Phase-1 设备监控扩展**（远程监控），暂不接入飞控、不做远程控制。

## 1. 背景与目标

### 1.1 现状
- 树莓派5 通过 CAN 接收 MPPT/BMS/DCDC 数据，经**串口数传**单向下传给地面 Qt 上位机（详见 [01_设备监控架构](./01_设备监控架构.md)）。
- 已接入 4G 物联网模块（SIM7600G-H，参考 [4G模块调试指南](./lingyun01/物联网模块/4G模块调试指南.md)）。

### 1.2 本次目标
- 新增**第二条 4G 公网监控链路**：机载数据经 4G 上报到**公有云服务器**，支持手机/电脑浏览器异地远程查看。

### 1.3 范围边界（重要）
- **4G 只做远程监控（数据上报告警）**，不做远程控制。
- **数传仍为本地实时操作通道**（控制指令、高频遥测）。
- 两条链路**分工互补，不做冗余主备**。

## 2. 双链路分工

| 维度 | 串口数传（本地） | 4G 公网（远程监控） |
|------|------------------|---------------------|
| 通信范围 | 近距离（地面站旁） | 广域、异地、可上公网 |
| 延迟 | 低（实时） | 高、不稳定 |
| 带宽 | 较高 | 受限 |
| 可靠性 | 高、可控 | 依赖运营商网络 |
| 角色 | **操作通道** | **监控通道** |
| 数据流向 | 双向（可下发控制） | 仅上行（上报） |

**结论**：数传负责"操作"，4G 负责"监控"，两者覆盖不同场景，合理且互补。

## 3. 系统拓扑

```
┌─────────────────────────── 机载（树莓派5）───────────────────────────┐
│                                                                       │
│  MPPT ──┐                                                            │
│  BMS  ──┼── CAN ─► bms/mppt/dcdc_node ─► monitor_node ─► link_node ──┼──► 串口数传 ─► 地面Qt上位机
│  DCDC ──┘                   │                              │         │        （本地操作通道）
│                             │                       [cloud_node]     │
└─────────────────────────────┼────────────────────────────────────────┘
                              │  MQTT over TLS
                              ▼
                    ┌───────────────── 公有云 ─────────────────┐
                    │   轻量应用服务器（公网IP）                  │
                    │   MQTT Broker (EMQX/Mosquitto)           │
                    │        │                                 │
                    │   后端服务 + Web 展示                     │
                    └──────────────────────────────────────────┘
                                    ▲
                                    │  HTTPS
                           手机 / 电脑浏览器（远程查看）
```

- 机载树莓派 = **数据源客户端（上报方）**，通过 4G 主动上报。
- 服务器 = 固定公网可达的接收/存储/展示端。

## 4. 数据分流策略

| 数据 | 走数传（本地） | 走 4G（远程监控） |
|------|:---:|:---:|
| 控制指令 | ✅ | ❌（禁用） |
| 高频实时遥测 | ✅ | — |
| 实时告警推送 | ✅ | ✅ |
| 低频周期遥测（如 1Hz） | — | ✅ |
| 运行日志 / 历史数据 | — | ✅ |
| 远程诊断心跳 | — | ✅ |

设备状态 JSON 帧很小（几十字节），按 1Hz 周期走 4G 对带宽无压力。

## 5. 4G 上报链路设计（cloud_node）

### 5.1 新增节点
在 [airship_link](./01_设备监控架构.md#L46) 旁新增 **cloud_node**（建议包名 `airship_cloud`），订阅与 link_node 相同的状态话题：

- `/bms/status`、`/mppt/status`、`/dcdc/status`
- `/monitor/device_alert`

> 复用 monitor_node 的聚合/告警逻辑，设备驱动层（bms/mppt/dcdc）完全不动。

### 5.2 传输协议
- **MQTT over TLS**（`mqtts://`，端口 8883）
- Broker：公有云上的 **EMQX**（功能全）或 **Mosquitto**（轻量）
- 认证：客户端用户名 + 密码（或证书），杜绝匿名接入

### 5.3 Topic 规划
| Topic | 内容 | QoS |
|-------|------|-----|
| `lingyun/device/heartbeat` | 机载在线心跳 | 1 |
| `lingyun/device/bms/status` | BMS 状态 | 0 |
| `lingyun/device/mppt/status` | MPPT 状态 | 0 |
| `lingyun/device/dcdc/status` | DCDC 状态 | 0 |
| `lingyun/device/alert` | 告警事件 | 1 |

### 5.4 上报数据格式（JSON）
沿用数传链路字段，按远程监控需求精简：

```json
{
  "t": 1785928200.123,
  "src": "lingyun01",
  "bms": {"online": true, "pack_v": 367.2, "pack_i": 0.0, "soc": 85,
          "max_v": 3.62, "min_v": 3.58, "diff_v": 0.04, "max_t": 32.5, "alarm": 0},
  "dcdc": {"online": true, "out_v": 48.1, "out_i": 5.2, "out_p": 250.0, "fault": 0}
}
```

### 5.5 上报频率
- 周期遥测：**1 Hz**（可配置参数）
- 告警：**事件触发即时上报**
- 心跳：**5 s**，用于判断机载在线

## 6. 云端方案对比与选型建议

机载数据上云有两条路径：**自建公有云服务器** 或 **运营商托管平台（OneNET）**。二者都可用 MQTT 接入，区别在于"谁来维护"。

### 6.1 两种方案对比

| 维度 | OneNET 托管平台 | 公有云服务器（自建） |
|------|----------------|---------------------|
| 服务器 | 平台提供，不用管 | 自己租一台、自己配置 |
| MQTT Broker | 平台自带，直接用 | 自己装 EMQX/Mosquitto |
| 后端/数据库 | 平台提供（存储/查询） | 自己写后端、自己建库 |
| 可视化 | 拖拽式数据大屏，现成 | 自己写 Web 前端 |
| 告警通知 | 平台支持（短信/推送） | 自己接通知服务 |
| 上手难度 | 低、快 | 高，需会运维 |
| 数据自主可控 | 数据托管在运营商 | 完全自主可控 |
| 定制自由度 | 受平台规则限制 | 完全自由 |
| 费用 | 按功能/用量 | 按服务器规格 + 带宽 |

> 类比：OneNET 像"租房"（拎包入住），公有云自建像"买房"（自己装修维护）。

### 6.2 选型建议

- **倾向省事、快速上线、单设备远程监控** → 选 **OneNET 托管平台**：机载 `cloud_node` 通过 MQTT 接入 OneNET，用数据可视化 View 拖出监控大屏，省去自建后端与运维。
- **倾向数据完全自主可控、深度定制** → 选 **公有云自建**。

> 当前文档暂以 **公有云自建** 为主方案（见 6.3），OneNET 作为可选替代路径，最终选型待定。

### 6.3 公有云自建方案（主方案）

**选型**：轻量应用服务器（阿里云 / 腾讯云 / 华为云），自带公网 IP，7×24 稳定。

**服务器组件**：
| 组件 | 作用 | 建议 |
|------|------|------|
| MQTT Broker | 接收机载上报 | EMQX / Mosquitto |
| 后端服务 | 订阅 broker、落库 | Node.js / Python 均可 |
| 数据库 | 历史数据存储 | SQLite / PostgreSQL |
| Web 展示 | 远程查看页面 | 简单 HTML + 图表 |

**安全基线**：
- 仅开放必要端口（如 8883 给 MQTT、443 给 HTTPS），其余关闭
- MQTT 启用 TLS + 账号认证
- 服务器 SSH 用密钥登录，禁用密码

## 7. 安全与控制边界（强制约束）

1. **4G 链路只做数据上报，不接收任何控制指令**——避免远程操作风险。
2. 若未来确需远程控制，必须先设计**二次授权 + 安全校验**，并遵循
   `safety_status.safe_to_control` 约束（详见项目工程约束），当前阶段**不实现**。
3. 所有 4G 通信走加密信道（TLS），机载侧保管好账号凭据。

## 8. 与现有架构的关系

- 复用 [airship_msgs](./01_设备监控架构.md#L64) 消息定义与 monitor_node 告警。
- 新增 `airship_cloud` 包（参考 `airship_link` 范式），依赖 `airship_msgs`，保持向下 DAG。
- link_node（数传）与 cloud_node（4G）并行订阅、独立输出，互不影响。

## 附录 A. 基础概念说明

### A.1 什么是 MQTT

MQTT 是面向物联网设备的**轻量通信协议**，采用**发布/订阅（Pub/Sub）**模型：

- 设备把数据"发布"到某个主题（Topic），中间由 Broker（代理）转发
- 订阅了该主题的设备即可收到数据，发布方与订阅方互不感知

| | HTTP | MQTT |
|------|------|------|
| 模型 | 请求/响应（一问一答） | 发布/订阅（邮局转发） |
| 适用 | 网页、API | 设备批量上报、低功耗 |
| 资源占用 | 高 | 极低（省流量省电） |
| 断线重连 | 麻烦 | 内置（心跳/遗嘱机制） |

机载 `cloud_node` 即采用 MQTT over TLS 上报设备状态。

### A.2 什么是物联网卡

物联网卡（物联卡）是运营商面向 IoT 设备提供的**专用上网 SIM 卡**，特点：

- 流量价格低、专用号段
- 可通过运营商平台（如 OneNET）统一管理、查询流量
- 需实名认证后使用，建议走运营商官方渠道办理，避免"黑卡"（易虚量、随时停服）

### A.3 MQTT 是物联卡独有功能吗？

**不是。** 三者为相互独立的组成部分：

- **MQTT** = 通信协议（发消息的方式），全网通用，任何有网络的设备都能用
- **物联卡** = 上网通道（SIM 卡）
- **云平台** = 数据接收/存储的地方

普通手机卡同样可用 MQTT 上云；物联卡也可用 HTTP/TCP 等协议，并不强制 MQTT。

### A.4 OneNET 配套服务

OneNET 是运营商托管的物联网 PaaS 平台，除卖物联卡外还提供：

| 服务 | 作用 |
|------|------|
| 设备接入 | MQTT/Modbus/HTTP/TCP 透传/NB-IoT 等协议接入 |
| 数据存储/查询 | 设备状态存储与查询 |
| 数据可视化 View | 拖拽式免编程搭建监控大屏 |
| 消息队列 MQ | 高并发消息中间件 |
| 远程升级 OTA | 终端 FOTA/SOTA 升级 |
| 位置能力 LBS | Wifi/基站定位、轨迹 |
| 视频能力 Video | 国标视频监控平台 |
| 人工智能 AI | 人脸/图像识别等 API |

这些能力可组合用于远程监控场景，避免自建后端与运维。

## 附录 B. NAT / 公网 IP 与云端方案选型

### B.1 "能上网" ≠ "能被访问"

关键区分两个方向：

- **主动发起（往外）**：树莓派 → 4G → 公网服务。✅ 可以。
- **被动接收（进来）**：手机/电脑 → 公网 → 树莓派。❌ 一般不行。

运营商给 4G/手机/普通宽带分配的是**共享、不固定、不对外可达的内网地址**（CGNAT），公网设备只知道"大楼地址"，找不到具体"房间"，因此**进不来**。手机用 4G 上网同理——它能主动连别人，别人无法直接连它。

> **一句话：4G/手机/普通家庭宽带上网 = "只能出去，不能进来"。**

### B.2 局域网 vs 公网

| | 局域网（内网） | 公网 |
|------|--------------|------|
| 使用的 IP | 私有 IP（如 `192.168.x.x`） | 公网 IP（全球唯一） |
| 互访 | 直接访问，无限制 | 需公网可达入口 |
| 例子 | 同一 WiFi 下电脑→`192.168.1.10` | 公网设备访问需公网 IP |

- **私有 IP**（`192.168.x.x` / `10.x.x.x` / `172.16~31.x.x`）：仅局域网内有效，出了局域网失效。
- **公网 IP**：全球唯一，公网可直接访问。

### B.3 公网 IP 需要申请吗？

| 场景 | 是否需要申请 |
|------|-------------|
| 公有云服务器 | 不用，买服务器自带公网 IP |
| 公司/家庭普通宽带 | 一般要向运营商申请，且常被拒/只给动态 IP |
| OneNET 等托管平台 | 不用，平台自己处理 |

### B.4 三种云端方案对比

| 维度 | 方案一 自建公有云服务器 | 方案二 云平台（OneNET） | 方案三 宽带+公网IP/内网穿透 |
|------|:---:|:---:|:---:|
| 服务器 | 租云服务器，自带公网 IP | 平台提供，不用管 | 公司/家里小电脑 |
| 公网入口 | 自带 | 平台处理 | 需公网 IP 或穿透 |
| 数据自主可控 | 完全 | 托管在运营商 | 完全 |
| 定制自由度 | 完全自由 | 受平台规则限制 | 完全自由 |
| 开发/运维成本 | 高 | 低 | 中 |
| 上手速度 | 慢 | 快 | 中 |
| 长期成本 | 服务器月租 | 按功能/用量 + 物联卡流量 | 买断硬件（穿透服务可能少量费用） |

### B.5 方案一 vs 方案二：如何选

- **方案一（自建）**：数据完全自主可控、可深度定制 → 适合对数据/规则高度敏感、需深度定制。
- **方案二（云平台）**：省事省运维、快速上线、有现成大屏/告警 → 适合单设备远程监控、快速验证。
- **可结合**：用方案二做接入+大屏，同时把数据抽取到自建服务器做长期存储/深定制，兼顾省事与自主。

> 当前文档第 6 章暂以**方案一（公有云自建）**为主方案，方案二（OneNET）为可选替代路径，最终选型待定。
