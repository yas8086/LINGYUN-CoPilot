## 0. 整体心智模型

ROS2 是一个 **分布式通信框架**。用一个"公司通信系统"来类比：

| ROS2 概念 | 类比 | 一句话 |
|-----------|------|--------|
| **节点 Node** | 部门员工 | 一个独立的任务单元 |
| **话题 Topic** | 公司广播/公告栏 | 单向持续广播数据 |
| **消息 Msg** | 公告的内容格式 | 数据的结构定义 |
| **服务 Service** | 打电话问前台 | 一次性请求-应答 |
| **动作 Action** | 派任务+进度反馈 | 长任务，可取消可反馈 |
| **参数 Parameter** | 员工档案里的配置项 | 节点可配置项 |
| **Master/Daemon(ROS1)** | 总机 | ROS2 已去掉，改为分布式发现 |

**ROS2 与 ROS1 最大的区别**：ROS1 有个中央节点 `master` 负责让各个程序互相找到对方，ROS2 用 **DDS（Data Distribution Service）** 做 **分布式自动发现**——没有中央节点，每个程序自己去发现别人。这是 ROS2 更健壮、更适合嵌入式/机器人的根本原因。

**一句话选型**：数据流用话题，调用用服务，长任务用动作，可配置项用参数。

## 1. 消息 Msg —— 数据的"结构定义"

话题上流动的是 **消息（Message）**。消息用 `.msg` 文件定义，编译时自动生成 C++/Python 类。

实例：`src/airship_msgs/msg/BmsStatus.msg`

```txt
std_msgs/Header header    # 标准头(含时间戳 stamp)

bool online               # CAN 链路是否在线
float32 pack_voltage      # 电池包总压 [V]
float32 pack_current      # 电池包总电流 [A]
float32 soc               # 荷电状态 [0-100 %]
float32[256] cell_voltages  # 定长数组: 单体电压
float32[256] cell_temps     # 定长数组: 单体温度
uint16 fault_word1        # 一级故障字
uint8  alarm_level        # 告警级别
```

**关键点：**

1. **字段类型**：`bool / uint8 / uint16 / float32 / float32[256]` 等。数组是定长的。
2. **`std_msgs/Header header`**：几乎每个消息第一个字段都是它。它含 `stamp`（时间戳）和 `frame_id`（坐标系名）。**每条传感器消息必须带时间戳**——接收方这样才能判断数据的"新鲜度"。
3. **注释 `#`**：写清楚单位很重要，避免把"V"当成"mV"用。

在 C++ 代码里，你看到的是生成的类：

```cpp
auto msg = airship_msgs::msg::BmsStatus();   // 生成的C++类
msg.header.stamp = this->now();               // 写时间戳
msg.pack_voltage = 411.2f;
```

### 为什么要有独立的 `airship_msgs` 包？

因为 BMS、MPPT、DCDC、Monitor 四个节点都要用 `BmsStatus`、`DeviceAlert` 这些消息。如果消息定义在某个节点包里，就会形成 **A 依赖 B、B 又依赖 A 的循环依赖**。把消息单独放一个底层包，所有节点都只依赖它，依赖关系就变成单向的（DAG）。

### 消息类型的三段式命名

`airship_msgs::msg::BmsStatus` 分层：
- `airship_msgs`：**包名**（package）
- `msg`：类型类别（消息，按功能有 `srv`/`action`/`interface`）
- `BmsStatus`：消息名

**这个分层是"一半你定、一半 ROS2 定"**：

| 段 | 谁定的 |
|----|--------|
| `airship_msgs` | 你定的（包名） |
| `msg` | **ROS2 固定约定**，不能改（消息用 `msg`、服务用 `srv`、动作用 `action`） |
| `BmsStatus` | 你定的（消息名） |

### `msg.header.stamp` 字段从哪来、为何能赋值？

`stamp` 不是手写成员，而是**消息层层嵌套定义、编译时自动生成**的。走三层嵌套：

```
msg (BmsStatus)
 └── .header   → std_msgs::msg::Header   (你在 .msg 里写 std_msgs/Header header 生成)
      └── .stamp  → builtin_interfaces::msg::Time  (Header 里写 builtin_interfaces/Time stamp)
           └── .sec / .nanosec  → 真正的整数
```

- `std_msgs/Header` 定义：`builtin_interfaces/Time stamp` + `string frame_id`
- `builtin_interfaces/Time` 定义：`int32 sec` + `uint32 nanosec`

**为什么能直接 `msg.header.stamp = this->now()`**：`rclcpp::Time` 提供了一个隐式转换运算符 `operator builtin_interfaces::msg::Time() const`，编译器自动把 `rclcpp::Time` 填进 `sec`/`nanosec`。等价于手写 `msg.header.stamp.sec = ...; msg.header.stamp.nanosec = ...;` 的语法糖。

两条规则：**谁发布、谁打时间戳**；`rosidl_generate_interfaces` 负责把 `.msg` 编译成上述 C++ 类。

## 2. 节点 Node —— 最小运行单元

节点是 ROS2 的 **最小运行单元**。一个 ROS2 程序通常是一个或多个节点。

实例：`src/airship_bms/src/bms_node.cpp`

```cpp
class BmsNode : public rclcpp::Node        // 继承 Node 基类
{
public:
  explicit BmsNode(const rclcpp::NodeOptions & options = rclcpp::NodeOptions())
  : rclcpp::Node("bms_node", options),      // 节点名 "bms_node"
    can_("can0"),
    running_(false)
  {
    // 构造函数里: 声明参数、创建发布器、启动线程...
  }
```

**节点名** `"bms_node"` 用于 ROS2 网络中的唯一标识。整个系统里节点名不能重复（除非用命名空间）。

### 节点生命周期（main 函数）

```cpp
int main(int argc, char ** argv)
{
  rclcpp::init(argc, argv);                       // ① 初始化运行时
  rclcpp::spin(std::make_shared<BmsNode>());      // ② 进入事件循环
  rclcpp::shutdown();                             // ③ 清理退出
  return 0;
}
```

- **`init`**：建立与 DDS 网络的连接，解析命令行参数。
- **`spin`**：**阻塞执行**，反复处理所有"回调"（收到消息、定时器触发）。没有回调时它大部分时间在等待。
- **`shutdown`**：优雅退出。

> **BMS 节点的特殊设计**：它用 `std::thread(&BmsNode::receive_loop, this)` 开了 **独立线程** 去读 CAN 数据，而 `spin` 只处理 ROS2 事件。这种"设备读取线程 + ROS 事件循环"分离的模式，在嵌入式驱动里很常见——因为 CAN 读取是阻塞的，不能塞进 spin 的回调里。

### 包（Package）是什么？和节点一一对应吗？

**包是"编译/分发单元"，不是"运行单元"；节点是"运行单元"。** 两者不一 一对应：

- **包** = 一组能一起编译、一起安装的代码（`airship_utils` 甚至没有节点，只有库+测试）。
- **节点** = 运行时的一个 `rclcpp::Node` 对象。
- 一个包可以编译出**多个节点**、多个库、多个消息定义。

**行业叫法**：`package`（包）是 **ROS 生态自己的术语**，不是通用软件工程术语。在 ROS 社区大家都懂；在通用软件工程里更常叫"模块/库/组件"。

### 一个 ROS2 程序 vs 一个 ROS2 系统？

- **一个 ROS2 程序（可执行文件）**：一个编译出的可执行文件（如 `bms_node`），运行后通常是一个进程，代表"一台设备上的一个运行单元"。
- **一个 ROS2 系统**：由**分布在多台设备、多个进程里的所有节点**共同组成的整体（如整个 LINGYUN-CoPilot = bms + mppt + dcdc + monitor + link）。

**"系统"是逻辑上的**——不依赖中央进程，靠 DDS 让所有节点自动互相发现、连成整体。

### 节点是进程吗？多个文件能组成一个节点吗？

**节点 ≠ 进程**（一个是 ROS 概念，一个是操作系统概念）：

```
进程(process) = 操作系统概念，独立的内存空间
节点(node)    = ROS2 概念，一个 rclcpp::Node 对象
一个进程可包含 1 个或多个节点
```

- **多个 .cpp 文件能组成一个节点**：把多个源码一起写进同一个 `add_executable`，编译成同一个可执行文件，运行时就是一个节点。但**全工程只能有一个 `main()`**。
- **怎么区分一个节点**：`new` 一次的 `rclcpp::Node` 实例 = 一个节点，靠**唯一节点名**区分（同进程内节点名不能重复）。用 `ros2 node list` 列出系统中的所有节点名。

### 能 `new` 多个相同的节点吗？归谁管理？

**能**，class 是模板，可创建多个实例。但**同进程内节点名不能重复**，否则第二个会抛异常崩溃。需用 `NodeOptions` 设置不同节点名/命名空间来区分：

```cpp
rclcpp::NodeOptions opts1; opts1.node_name("main"); opts1.namespace_("battery");
rclcpp::NodeOptions opts2; opts2.node_name("backup"); opts2.namespace_("battery");
auto node1 = std::make_shared<BmsNode>(opts1);
auto node2 = std::make_shared<BmsNode>(opts2);
```

**归谁管理**：
- **进程内**：节点交给执行器 `Executor`（`rclcpp::spin` 或 `MultiThreadedExecutor`）驱动运转。
- **系统层面**：注册到 ROS2 分布式 **graph**，靠 DDS 自动发现，无中央管理者。

## 3. 话题 Topic —— 单向持续数据流

话题是 **发布（publish）/订阅（subscribe）** 模型。多个节点靠话题通信，**发送方和接收方完全解耦**。

### 3.1 发布方（Publisher）

BMS 节点发布电池状态，`bms_node.cpp`：

```cpp
status_pub_ = this->create_publisher<airship_msgs::msg::BmsStatus>("/bms/status", rclcpp::QoS(10));
```

话题名是 `/bms/status`。`/` 开头是 **全局命名**，任何节点都能直接订阅。

发布时手动填充并发送，`bms_node.cpp` `publish_status()`：

```cpp
auto msg = airship_msgs::msg::BmsStatus();
msg.header.stamp = this->now();
msg.pack_voltage = pack_voltage_;
msg.soc = soc_;
msg.max_cell_voltage = ...;   // 遍历256节算最高/最低
msg.fault_word1 = fault_word1_;
status_pub_->publish(msg);    // 发布!
```

### 3.2 订阅方（Subscriber）

Monitor 节点订阅同一个话题，`src/airship_monitor/src/monitor_node.cpp`：

```cpp
bms_sub_ = this->create_subscription<airship_msgs::msg::BmsStatus>(
  "/bms/status", rclcpp::QoS(10), std::bind(&MonitorNode::on_bms, this, _1));
```

三个参数：
1. **话题名** `/bms/status` —— 必须与发布者一致
2. **QoS** —— 传输质量配置
3. **回调函数** `on_bms` —— **每当收到一条消息就调用一次**

回调实现：

```cpp
void on_bms(const airship_msgs::msg::BmsStatus::SharedPtr msg)
{
  last_bms_time_ = this->now();          // 记录收到时间(供看门狗)
  if (msg->alarm_level != last_bms_alarm_) {   // 告警级别变化了才发告警
    publish_alert(...);
    last_bms_alarm_ = msg->alarm_level;
  }
}
```

**注意 `msg->` 用箭头**：`SharedPtr` 是智能指针，所以用 `->` 访问字段。

### 3.3 配对关系图

```
[BMS节点]  --publish-->  /bms/status  --subscribe-->  [Monitor节点]
[MPPT节点] --publish-->  /mppt/status --subscribe-->  [Monitor节点]
[DCDC节点] --publish-->  /dcdc/status --subscribe-->  [Monitor节点]
                                          |
                                    [看门狗定时器]
                                          |
              --publish--> /monitor/device_alert (告警)
```

**核心思想**：BMS 节点 **根本不认识** Monitor 节点。它只是往 `/bms/status` 上发数据。将来你加记录日志的节点、加遥测上传节点，都只需要订阅这个话题，**BMS 节点一行都不用改**。这就是话题解耦的价值。

### 3.4 手动调试话题（工具链预告）

```bash
ros2 topic list                    # 列出所有话题
ros2 topic echo /bms/status        # 实时打印话题内容
ros2 topic info /bms/status        # 查看发布者/订阅者数量
ros2 topic hz /bms/status          # 统计发布频率
```

### 3.5 底层通信：DDS 如何自动发现？

ROS2 用 **RTPS 协议**（跑在 UDP/IP 之上），发现分两个阶段：

1. **参与者发现（PDP）**：新节点上线时，向**固定组播地址**发"我是谁"的通告，其他参与者单播回复 → 双方互相认识。
2. **端点发现（EDP）**：互相认识后，交换各自的**话题/发布者/订阅者清单** → 比对出"你发 `/bms/status`，我要订阅它" → 建立点对点数据连接。

**关键点**：
- **`ROS_DOMAIN_ID` 不同则互相发现不了**（相当于隔离成不同"房间"）。
- 默认是**组播动态发现**（即插即用）；也支持静态发现/Discovery Server（跨网段、组播不可用时）。

### 3.6 进程间通信 vs 进程内通信？

**默认是进程间**（即使同机也走 UDP loopback），有序列化+拷贝开销；**同进程内可走零拷贝快速通道**。

| 维度 | 进程间（默认） | 进程内（优化） |
|------|--------------|--------------|
| 数据路径 | 序列化→网络→反序列化 | 直接传 `shared_ptr` |
| 序列化 | 需要 | 不需要 |
| 内存拷贝 | 多次 | 零拷贝 |
| 适用 | 不同进程/不同机器 | 同进程内 pub/sub |
| 代码写法 | 一样 | 一样（透明） |

> 用 `MultiThreadedExecutor` 把多个节点放进同一进程时，它们之间自动享受进程内优化。

### 3.7 与传统 IPC 的本质区别？

ROS2 的传播是**分布式发布-订阅中间件（DDS）**，不是传统 IPC。传统 IPC（管道/socket/共享内存）是**点对点、本地、无发现、无类型安全、无 QoS**；ROS2 的创新在于：

- **匿名发布-订阅**：发布者不知道谁订阅，订阅者不知道谁发布，完全解耦。
- **跨进程、跨机器透明**：同一套 API，本地/远程写法完全一样。
- **接口独立 + 代码生成**：`.msg` 定义接口，自动生成 C++/Python 代码。
- **运行时类型检查**：发布/订阅会比对消息类型哈希，类型不匹配直接报警。
- **QoS 服务质量**：可靠性/持久性/队列深度等策略，传统 IPC 没有。
- **自动发现 + 无中央节点**：比 ROS1 的 master 更健壮。
- **可替换 DDS 实现**：通过 RMW 抽象，可换 FastDDS / CycloneDDS 等，不影响代码。

**一句话**：传统 IPC 是"两台机器拉线传字节"；ROS2 是"消息总线 + 带类型数据 + 自动发现路由 + 服务质量"。

## 4. 定时器 Timer

ROS2 里常用 **定时器** 做周期性任务。Monitor 节点的看门狗，`monitor_node.cpp`：

```cpp
watchdog_timer_ = this->create_wall_timer(
  std::chrono::milliseconds(static_cast<int>(1000.0 / watchdog_hz_)),  // 周期
  std::bind(&MonitorNode::watchdog_callback, this));                    // 回调
```

每 `1/watchdog_hz_` 秒触发一次 `watchdog_callback`，检查各设备是否超时离线。定时器回调也是由 `spin` 驱动的。

## 5. 服务 Service —— 一次性请求-应答

> **本项目暂未用到**，但属核心概念，必须掌握。

**适用场景**：需要"问一句、答一句"的操作，比如"重置看门狗"、"读取当前配置"、"执行一个校准"。

### 服务定义（.srv）

```txt
# 请求(Request)
uint32 request_id
---
# 响应(Response)
bool success
string message
```

`---` 上方是请求，下方是响应。

### 服务端（Server）——提供服务的节点

```cpp
srv_ = create_service<airship_msgs::srv::ResetDevice>("reset_device",
  [this](const std::shared_ptr<airship_msgs::srv::ResetDevice::Request> req,
         std::shared_ptr<airship_msgs::srv::ResetDevice::Response> res) {
    res->success = reset_done();
    res->message = reset_done() ? "ok" : "failed";
  });
```

### 客户端（Client）——调用服务的节点

```cpp
client_ = create_client<airship_msgs::srv::ResetDevice>("reset_device");
while (!client_->wait_for_service(1s)) {}            // 等服务上线
auto req = std::make_shared<...::Request>();
req->request_id = 42;
auto future = client_->async_send_request(req);      // 异步发送
auto resp = future.get();                            // 等待响应
```

### 手动调试服务

```bash
ros2 service list
ros2 service call /reset_device airship_msgs/srv/ResetDevice "{request_id: 42}"
```

## 6. 动作 Action —— 长任务 + 进度反馈

> 同样项目里没用到。**服务 vs 动作**：服务是"问完就完"，动作是"派活 + 中途反馈 + 可取消"。

**适用场景**：导航到某点、走一段航迹、充放电一个循环——耗时几秒到几分钟，需要进度反馈，可能中途取消。

### 动作定义（.action）

```txt
# 目标(Goal)
float32 target_position
---
# 反馈(Feedback)
float32 current_position
---
# 结果(Result)
bool success
```

三部分：目标 → 反馈（循环）→ 结果。

### 动作的三个通信通道

动作在底层由 **3 个话题 + 2 个服务** 组成，但上层封装成简单 API：

- `goal` 话题：发送执行目标
- `feedback` 话题：服务端周期性回传进度
- `result` 话题：结束时返回结果
- 取消服务、状态查询服务

### 简单 API（C++ 风格）

服务端用 `rclcpp_action::create_server`，客户端用 `rclcpp_action::create_client`，客户端 `async_send_goal` 后，通过回调接收 feedback 和 result。

## 7. 参数 Parameter —— 可配置项

参数是 **节点的配置项**，可以启动时设置，也可以在运行中动态修改（`rclcpp` 支持动态参数回调）。

`bms_node.cpp`：

```cpp
can_if_ = this->declare_parameter("can_interface", std::string("can0"));
cell_count_ = static_cast<uint16_t>(this->declare_parameter("cell_count", 0));
```

`monitor_node.cpp`：

```cpp
watchdog_hz_ = this->declare_parameter("watchdog_rate_hz", 1.0);
timeout_s_ = this->declare_parameter("link_timeout_s", 3.0);
```

- `declare_parameter("名字", 默认值)`：声明一个参数并给默认值
- 返回值为参数当前值

**好处**：这些值不用改代码、重新编译，只需在 launch 文件或命令行里改。`src/airship_bringup/config/airship_params.yaml` 就是集中管理这些参数的地方（模块2会讲）。

### 命令行设置参数

```bash
ros2 run airship_bms bms_node --ros-args -p can_interface:=can1 -p cell_count:=102
```

### 动态参数（概念）

ROS2 可以在运行时改参数，通过 `add_on_set_parameters_callback` 注册回调，收到新值后校验并执行。适合"不用重启就能调 PID 参数"这类需求。

## 8. QoS —— 服务质量

QoS 决定 **消息传输的可靠性**。代码里到处是 `rclcpp::QoS(10)`。

`QoS(10)` 里的 **10 是队列深度**——如果订阅者处理不过来，最多缓存 10 条，满了就丢最旧的。

QoS 关键维度：

| 维度 | 选项 | 含义 |
|------|------|------|
| **可靠性 Reliability** | `RELIABLE` / `BEST_EFFORT` | 可靠=保证送达(可重传)；尽力=丢了就算了(低延迟) |
| **持久性 Durability** | `TRANSIENT_LOCAL` / `VOLATILE` | 订阅前发布的历史数据要不要保留 |
| **队列深度 History** | `KEEP_LAST(N)` / `KEEP_ALL` | 保留最近N条 还是 全保留 |

**选择原则**：
- 电池电压、CAN 原始数据这些 **实时传感器流** → `BEST_EFFORT`（丢一条没关系，要低延迟）
- 控制指令、告警、配置这类 **重要的** → `RELIABLE`（保证送达）

> **陷阱警告**：发布者和订阅者的 QoS **必须兼容**，否则通信会失败（ros2 会报错）。这是 ROS2 新手最常见的坑之一。

## 9. 时间戳与时钟

每条带 `Header` 的消息都有 `stamp`：

```cpp
msg.header.stamp = this->now();   // 打上当前时刻
```

`this->now()` 返回 `rclcpp::Time`，默认用 **系统时钟**（也支持仿真时钟 `/clock`，用于仿真时间同步）。

Monitor 节点用它做超时判断，`monitor_node.cpp`：

```cpp
const double age = (this->now() - last_time).seconds();   // 距上次收到数据多久
if (age > timeout_s_) { publish_alert(...); }             // 超过阈值判离线
```

减法 `Time - Time` 得到时长，`.seconds()` 转成秒。

**时间戳的价值**：接收方拿到数据 + 时间戳，就能知道数据的"新鲜度"，判断设备是否在线、数据是否过期。

## 10. 日志 Logging

不用 `printf`，ROS2 用 `RCLCPP_*` 宏：

```cpp
RCLCPP_WARN(this->get_logger(), "打开 CAN 接口 %s 失败, 稍后重试", can_if_.c_str());
```

```cpp
RCLCPP_WARN(this->get_logger(), "[%s][dev=%u] %s", level, device_type, message.c_str());
```

**级别从低到高**：

| 宏 | 级别 | 用途 |
|----|------|------|
| `RCLCPP_DEBUG` | DEBUG | 调试细节 |
| `RCLCPP_INFO` | INFO | 一般信息 |
| `RCLCPP_WARN` | WARN | 警告，不致命 |
| `RCLCPP_ERROR` | ERROR | 错误 |
| `RCLCPP_FATAL` | FATAL | 致命错误 |

用 `RCLCPP_*` 的好处：支持结构化的日志、可以按级别过滤、能被 rqt_console 等工具实时查看。

## 11. 执行器 Executor 与 spin —— 多线程

`rclcpp::spin(node)` 是 **单线程执行器**——所有回调（话题、定时器、服务）都在 **一个线程** 里排队执行。**回调不能耗时太久**，否则会阻塞其他回调。

BMS 节点怎么处理这一点？`bms_node.cpp`：

```cpp
receive_thread_ = std::thread(&BmsNode::receive_loop, this);  // 独立线程读CAN
```

**阻塞的 CAN 读取被放到独立线程**，而 ROS2 回调（发布）留在 spin 的线程里。这是嵌入式驱动 **线程模型** 的典型做法。

### 多线程执行器（概念）

如果节点回调多且需要并行，可以用多线程执行器：

```cpp
rclcpp::executors::MultiThreadedExecutor executor;
executor.add_node(std::make_shared<BmsNode>());
executor.add_node(std::make_shared<MonitorNode>());
executor.spin();
```

甚至可以在 **一个进程** 里跑多个节点（SAME process），减少进程开销。这是解决"多进程节点效率低"问题的手段之一。

## 12. 生命周期节点（概念，进阶）

ROS2 有 **生命周期节点**（Lifecycle Node），状态机：
`Unconfigured → Inactive → Active → Finalized`

- 设备驱动常用它：**Active 之前不发布数据**，保证启动顺序
- 你的 BMS 节点当前是普通节点，构造函数里 `can_.open()` 失败只是 `WARN` 继续跑。如果改成生命周期节点，可以让它先进入 `Inactive`，确认 CAN 好了再 `Active` 开始发布——更规范（属进阶，了解即可）
