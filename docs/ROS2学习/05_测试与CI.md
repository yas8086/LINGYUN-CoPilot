## 0. 为什么嵌入式/机器人代码必须测试

ROS2 节点代码直接耦合了话题通信，**很难离线验证**。你的项目记忆里强调"核心业务逻辑要抽成 ROS 无关的纯函数 + gtest 单元测试"——原因就是：

- 节点 → 依赖 ROS 运行时，跑起来才能测
- **纯函数**（无状态、无副作用）→ 不依赖 ROS，**任何环境都能测**，还能离线验证

所以测试的第一条原则是：**把能测的逻辑抽成纯函数库**（如 `airship_utils`），再针对库写测试。

## 1. gtest 基础

**gtest（GoogleTest）** 是 C++ 最主流的单元测试框架。ROS2 用 `ament_add_gtest` 封装它。

### 1.1 测试文件的三个组成部分

一个测试文件（如 [test_math_utils.cpp](file:///home/lingyun01/LINGYUN-CoPilot/src/airship_utils/test/test_math_utils.cpp)）包含：

1. **包含头文件**：`#include <gtest/gtest.h>` + 被测库的头文件
2. **测试用例**：`TEST(...)` / `TEST_F(...)` / `TEST_P(...)`
3. （可选）**main 函数**：用 `ament_add_gtest` 时**不需要**写 main，会自动注入

```cpp
#include <gtest/gtest.h>
#include "airship_utils/math_utils.hpp"

TEST(NormalizeAngleTest, WrapsPositiveOverflow)
{
  double result = normalize_angle(7.0f);
  EXPECT_NEAR(result, 7.0 - 2.0 * M_PI, 1e-4);
}
```

### 1.2 测试用例语法

```
TEST(分组名 TestSuiteName, 用例名 TestName)
```

- 分组名：把相关用例归组（如 `NormalizeAngleTest`）
- 用例名：具体测试什么（如 `WrapsPositiveOverflow`）

一个测试用例里可以有多个断言。

## 2. 断言宏：EXPECT_* vs ASSERT_*

你的测试文件里两种都用到了，区别很关键：

| 宏 | 失败时行为 | 使用场景 |
|----|-----------|---------|
| `EXPECT_*` | **继续执行**后面断言 | 默认，能一次看到多个失败 |
| `ASSERT_*` | **立刻中断**当前用例 | 前置条件不满足、后续无需执行 |

看 [test_math_utils.cpp](file:///home/lingyun01/LINGYUN-CoPilot/src/airship_utils/test/test_math_utils.cpp#L71-82) 的例子：

```cpp
TEST(AngleDiffTest, DifferenceIsBounded)
{
  for (size_t i = 0; i < 1000; ++i) {
    float diff = angle_diff(...);
    ASSERT_GT(diff, -static_cast<float>(M_PI));  // 越界就中断循环
    ASSERT_LE(diff, static_cast<float>(M_PI));
  }
}
```

这里用 `ASSERT_*`——一旦 diff 越界，说明实现有 bug，**继续算下去没有意义**，直接中断。

### 常用断言对照

| 断言 | 含义 |
|------|------|
| `EXPECT_EQ(a, b)` | a == b |
| `EXPECT_TRUE(x)` / `EXPECT_FALSE(x)` | x 为真/假 |
| `EXPECT_GT / LT / GE / LE` | > < >= <= |
| `EXPECT_NEAR(a, b, tol)` | 绝对误差内相等 |
| `EXPECT_FLOAT_EQ(a, b)` | float 专用相等 |
| `EXPECT_DOUBLE_EQ(a, b)` | double 专用相等 |
| `EXPECT_NO_THROW(...)` | 不抛异常 |
| `EXPECT_THROW(...)` | 应该抛异常 |

## 3. 浮点比较的"坑"（重要）

**不要用 `EXPECT_EQ` 直接比较浮点数**。看 [test_math_utils.cpp](file:///home/lingyun01/LINGYUN-CoPilot/src/airship_utils/test/test_math_utils.cpp#L189-200) 的注释：

```cpp
TEST(FloatingPointTest, FloatEqHandlesTinyDifferences)
{
  float a = 0.1f + 0.2f;
  EXPECT_FLOAT_EQ(a, 0.3f);   // ✓ 正确: 0.1+0.2 在二进制下不等于 0.3
  // EXPECT_EQ(a, 0.3f);      // ✗ 错误: 会偶发失败
}
```

**原因**：`0.1 + 0.2` 在二进制浮点里不等于 `0.3`。必须用浮点专用断言：

| 宏 | 说明 | 推荐 |
|----|------|------|
| `EXPECT_FLOAT_EQ(a, b)` | float，4 ULP 内相等 | ✓ |
| `EXPECT_DOUBLE_EQ(a, b)` | double，4 ULP 内相等 | ✓ |
| `EXPECT_NEAR(a, b, tol)` | 绝对误差 tol 内相等 | ✓ 最常用 |

## 4. 三种测试写法

你的测试文件非常完整地演示了三种写法：

### 4.1 `TEST()` —— 最基础

一个独立用例，不共享数据。前面 1.1 的例子就是。

### 4.2 `TEST_F()` + 测试夹具（Test Fixture）

当多个用例**共享同一套初始化数据**时，用夹具类封装 `SetUp`/`TearDown`。看 [test_math_utils.cpp](file:///home/lingyun01/LINGYUN-CoPilot/src/airship_utils/test/test_math_utils.cpp#L104-142)：

```cpp
class ClampTest : public ::testing::Test
{
protected:
  void SetUp() override { min_ = -10.0f; max_ = 10.0f; }  // 每个用例前执行
  void TearDown() override {}                              // 每个用例后执行
  float min_;
  float max_;
};

TEST_F(ClampTest, ClipsBelowMin)
{
  EXPECT_FLOAT_EQ(clampf(-100.0f, min_, max_), min_);
}
```

- 继承 `::testing::Test`
- `SetUp()`：每个用例执行前自动调用，初始化公共数据
- `TearDown()`：每个用例执行后调用，释放资源
- 用例名用 `TEST_F`（F = Fixture）

### 4.3 `TEST_P()` + 参数化测试

同一段逻辑对**多组输入**循环执行。看 [test_math_utils.cpp](file:///home/lingyun01/LINGYUN-CoPilot/src/airship_utils/test/test_math_utils.cpp#L149-179)：

```cpp
struct ClampTestCase { float input, lo, hi, expected; };

class ClampParameterizedTest : public ::testing::TestWithParam<ClampTestCase> {};

TEST_P(ClampParameterizedTest, ClampsToExpected)
{
  const auto & tc = GetParam();
  EXPECT_FLOAT_EQ(clampf(tc.input, tc.lo, tc.hi), tc.expected);
}

INSTANTIATE_TEST_SUITE_P(
  ClampVariants, ClampParameterizedTest,
  ::testing::Values(
    ClampTestCase{-50.0f, -10.0f, 10.0f, -10.0f},   // 低于下限
    ClampTestCase{3.0f, -10.0f, 10.0f, 3.0f},       // 正常区间
    ClampTestCase{10.0f, -10.0f, 10.0f, 10.0f}      // 上边界
  ));
```

- 继承 `TestWithParam<数据类型>`
- `GetParam()` 取当前数据
- `INSTANTIATE_TEST_SUITE_P` 喂入多组数据
- **同一逻辑测多组输入**，比写多个 `TEST` 简洁

## 5. 如何让一个包变得"可测试"

核心是**业务逻辑与 ROS 解耦**。你的 `airship_utils` 就是典范，看其 [CMakeLists.txt](file:///home/lingyun01/LINGYUN-CoPilot/src/airship_utils/CMakeLists.txt#L12-30)：

```cmake
# 编译成"库"(不是可执行文件)
add_library(${PROJECT_NAME}
  src/math_utils.cpp
  src/can_utils.cpp
)
```

**关键设计**：把纯逻辑（角度归一化、限幅、CAN 解析）编译成**库**，而不是塞进节点可执行文件里。这样测试程序只需要链接这个库，**不需要启动 ROS**。

### 挂接 gtest 测试

看 [CMakeLists.txt](file:///home/lingyun01/LINGYUN-CoPilot/src/airship_utils/CMakeLists.txt#L33-52)：

```cmake
if(BUILD_TESTING)
  find_package(ament_cmake_gtest REQUIRED)   # 找到 gtest

  ament_add_gtest(test_math_utils            # 生成测试可执行文件
    test/test_math_utils.cpp
  )
  if(TARGET test_math_utils)
    target_link_libraries(test_math_utils ${PROJECT_NAME})  # 链接被测库
  endif()
endif()
```

- `ament_add_gtest`：把测试源文件编译成测试可执行文件
- `target_link_libraries(... ${PROJECT_NAME})`：链接被测的 `airship_utils` 库

## 6. 代码规范检查 ament_lint

ROS2 提供一整套静态检查工具，保证代码风格统一。你的 CI 里用到了这些，[ci.yml](file:///home/lingyun01/LINGYUN-CoPilot/.github/workflows/ci.yml#L43-53)：

```bash
ament_uncrustify $CPP    # C++ 代码风格(缩进/括号等)
ament_cpplint $CPP       # C++ 风格/命名规范
ament_lint_cmake $CMAKE  # CMakeLists 规范
ament_xmllint $XML       # package.xml 规范
ament_flake8 $PY         # Python 规范
ament_pep257 $PY         # Python 文档规范
```

### 本地运行 lint

在包目录下，由 CMake 的 `ament_lint_auto` 自动生成 lint 测试：

```bash
colcon build --packages-select airship_utils
colcon test --packages-select airship_utils
colcon test-result --verbose    # 查看 lint 结果
```

> 注意：lint 检查**在 `BUILD_TESTING` 内**，各包 CMakeLists 里都有：
> ```cmake
> if(BUILD_TESTING)
>   find_package(ament_lint_auto REQUIRED)
>   ament_lint_auto_find_test_dependencies()
> endif()
> ```

### 闭源项目的处理

你的项目是闭源（license: Proprietary），`ament_copyright` 没有 proprietary 模板，会误报。解决方式（各包一致）：

```cmake
set(ament_cmake_copyright_FOUND TRUE)   # 跳过版权检查
```

同时 `package.xml` 里 license 设为 `Proprietary`。

## 8. CI 配置详解（GitHub Actions）

你的 [.github/workflows/ci.yml](file:///home/lingyun01/LINGYUN-CoPilot/.github/workflows/ci.yml) 是完整的 CI 范例。分两部分理解。

### 8.1 触发条件

```yaml
on:
  push:
    branches: [main, master]     # 推送到 main/master 时触发
  pull_request:                  # 有 PR 时触发
  workflow_dispatch:             # 支持手动触发
```

### 8.2 两个 Job

**① `lint`** —— 快速静态检查（不编译）：

```yaml
lint:
  runs-on: ubuntu-24.04
  container: osrf/ros:jazzy-ros-base      # 用官方 ROS2 Jazzy 容器
  steps:
    - uses: actions/checkout@v4           # 检出代码
    - name: Install ament linters
      run: apt-get install -y ros-jazzy-ament-lint-common
    - name: Run linters
      run: |
        source /opt/ros/jazzy/setup.bash
        ament_uncrustify $(find src -name '*.cpp' ...)
        ament_cpplint $(find src ...)
        ament_lint_cmake $(...)
        ament_xmllint $(...)
        ament_flake8 $(...)
        ament_pep257 $(...)
```

**② `build-test`** —— 编译 + 测试（矩阵，支持 x86_64 和 arm64）：

```yaml
build-test:
  strategy:
    matrix:
      include:
        - runs-on: ubuntu-24.04
          arch: x86_64
        - runs-on: ubuntu-24.04-arm      # arm64 runner
          arch: arm64
  runs-on: ${{ matrix.runs-on }}
  container: osrf/ros:jazzy-ros-base
  steps:
    - uses: actions/checkout@v4
    - name: Install dependencies
      run: |
        source /opt/ros/jazzy/setup.bash
        rosdep install --from-paths src --ignore-src -y --rosdistro jazzy   # 自动装依赖
    - name: Build
      run: colcon build --symlink-install --cmake-args -DCMAKE_BUILD_TYPE=Release
    - name: Test
      run: |
        colcon test --event-handlers console_cohesion+
        colcon test-result --verbose
    - name: Upload test results
      if: always()
      uses: actions/upload-artifact@v4      # 上传测试报告
```

### 8.3 CI 关键点

| 要点 | 说明 |
|------|------|
| **容器** | `osrf/ros:jazzy-ros-base` 提供干净的 ROS2 环境 |
| **rosdep** | 自动根据 package.xml 安装依赖 |
| **矩阵** | 同时验证 x86_64 和 arm64（你的树莓派是 arm64） |
| **测试** | `colcon test` + `colcon test-result` |
| **上传产物** | 测试 xml 报告可下载查看 |

> **arm64 的意义**：你的树莓派 5 是 arm64 架构，CI 里跑 arm64 能提前发现 ARM 特有的编译问题，不用等上真机。

## 9. 测试驱动开发的建议（针对本项目）

1. **抽纯函数**：把 CAN 解析、坐标转换、角度归一化等逻辑放进 `airship_utils` 库
2. **先写测试再实现**：TDD 思路，先定义输入输出，再写实现让测试通过
3. **边界条件必测**：NaN、极限值、负值、空数据（你的 `test_math_utils.cpp` 里 `TEST(ClampTest2, InvalidRangeBehaviour)` 就是测边界）
4. **浮点用专用断言**：永远用 `EXPECT_FLOAT_EQ` / `EXPECT_NEAR`
5. **CI 兜底**：把测试挂进 CI，每个提交自动跑，防止回归
