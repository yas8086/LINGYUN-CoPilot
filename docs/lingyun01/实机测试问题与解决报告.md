## 二、发现的问题与解决方案

### 问题 1：LoRa 温度恒为 0.00℃

**现象**：电脑通过 232 收到数传帧，LoRa 3 个节点温度全部 0.00℃，而集中器实际有温度数据。

**定位过程**：
1. 直连集中器 485 串口（独占方式）读原始响应 → 正常返回 26.8℃/26.6℃/24.0℃
2. 在 lora_node 加诊断日志打印实际发送的查询字节 → 发现实际查询地址为 **0x76B9/0x76BA/0x76BE**
3. 与协议正确地址 **0x76C1/0x76C2/0x76C6** 对比，少了 8

**根因**：`airship_params.yaml` 中 `temp_reg_addr: 30393` 配置错误。
- 30393 十进制 = **0x76B9**（集中器未映射地址，统一返回 raw=0）
- 正确值应为 30401 = **0x76C1**（协议温度寄存器）
- 注释写的是 0x76C1，但数值抄写错误

**解决**：修改 [airship_params.yaml](file:///home/lingyun01/LINGYUN-CoPilot/src/airship_bringup/config/airship_params.yaml) `temp_reg_addr: 30393 → 30401`，同步 install，重启服务。

**验证**：lora_node 查询 0x76C1/0x76C2/0x76C6 → 温度 26.8/26.7/24.1℃ ✅

### 问题 2：LoRa 温度探头 3/4/5 未采集

**现象**：实际有 6 个 LoRa 节点（1~5 温度探头 + 6 压力），但只配置采集了 1/2/6。

**定位**：检查 `node_ids: [1, 2, 6]`，缺失 3/4/5。直连验证 3/4/5 寄存器 0x76C3/0x76C4/0x76C5 均有正常温度。

**解决**：`node_ids` 补充为 `[1, 2, 3, 4, 5, 6]`，`node_types` 对应 5 个 temperature + 1 个 pressure。

---

### 问题 3：monitor_node 设备在线判定误判（已修复）

**现象**：can0 总线实际零数据（BMS/DCDC 均离线），但 monitor 日志显示 dev=1(BMS)/dev=3(DCDC) 间歇"上线"。

**根因**（代码审查确认）：
- [monitor_node.cpp](file:///home/lingyun01/LINGYUN-CoPilot/src/airship_monitor/src/monitor_node.cpp) 的 `check_link` 只看"是否收到该设备消息"（`last_time` 在 3s 内），**完全忽略消息内的 `online` 字段**
- 设备节点（bms_node/dcdc_node）在设备离线时仍每 3s 发布一次 `online=false` 兜底消息
- monitor 收到这些 offline 心跳也会刷新 `last_time` → 永远判定"在线"

**解决**（本次修复）：
- `on_bms/on_mppt/on_dcdc/on_backup` 回调改为**仅当 `msg->online=true` 时刷新链路时间戳与设备告警**，离线兜底消息不再驱动在线判定
- `on_lora` 改为仅当 `serial_online=true` 时刷新链路时间戳（告警逻辑仍处理所有消息以捕获状态变化）
- 离线判定仍由 `check_link` 基于"最后在线时间超时"完成，逻辑不变

**验证**：设备真实离线时（can0 无 DCDC/BMS 数据、12S 串口无响应），monitor 不再误判上线，正确保持"未上线"；编译与 alert_dedup 测试通过。

**状态**：✅ 已解决

### 问题 4：dcdc_hold 发送阻塞卡死

**现象**：can0 异常（ERROR-PASSIVE）时，dcdc_hold 进程卡死，不再正常循环（内核栈显示阻塞在 `sock_alloc_send_pskb`）。

**根因**：`SocketCanInterface` 使用**阻塞 socket**，CAN 接口异常（ERROR-PASSIVE/断线/发送队列满）时，`write()` 无限阻塞，导致保活进程卡死（违背"保活进程绝不能卡死"的设计目标）。

**解决**：
- [socketcan.cpp](file:///home/lingyun01/LINGYUN-CoPilot/src/airship_can/src/socketcan.cpp)：socket 创建后设 `O_NONBLOCK`
- `send()` 改为 `poll(POLLOUT)` 限时等待可写（默认超时 100ms），超时返回失败，调用方走重连/重试
- 接口增加 `timeout_ms` 参数（默认 100，向后兼容）

**验证**：can0 ERROR-PASSIVE 时 dcdc_hold 正常循环（wchan 从 `sock_alloc_send_pskb` 变为 `futex_wait_queue`），CPU 0.2% ✅

---

### 问题 5：dcdc_hold 无法感知"帧是否真正发出"

**现象**：`send()` 返回成功（socket 入队成功），但帧实际未到总线（can0 ERROR-PASSIVE 时 MCP2515 无法发送），dcdc_hold 无告警。

**解决**：在 [dcdc_hold.cpp](file:///home/lingyun01/LINGYUN-CoPilot/src/airship_dcdc/src/dcdc_hold.cpp) 增加 TX 计数监控：
- 新增 `read_tx_packets()` 读取 `/sys/class/net/<if>/statistics/tx_packets`
- 每周期 send 后对比 TX 计数：send 成功但计数未增长 → 每 5s 告警"控制帧未真正发出"

**验证**：can0 ERROR-PASSIVE 时正确输出告警；DCDC 接入后 TX 计数增长，告警消失 ✅

---

### 问题 6：DCDC 电压/电流/温度全为 0

**现象**：电脑数传帧中 DCDC `in_v/out_v/out_i/out_p/temp` 全为 0，`enabled=true, fault=4`。

**定位过程**：
1. 确认 dcdc_hold 每 200ms 发控制帧 `0x18EF3010` 和模拟量查询 `0x18D80047`
2. 监听 20s：模拟量查询发出 100 帧，**模拟量回应 `0x18D84700` 0 帧**（DCDC 不回应查询）
3. 分析 DCDC 状态帧 `0x18FF3247` 原始 8 字节 `04 8b 01 ee 01 34 00 54`，发现 Byte1~7 本身携带模拟量数据

**根因**：DCDC **状态帧** `0x18FF3247` 本身已携带完整模拟量（与模拟量回应同格式）：
- Byte1~2 输入电压（1V/BIT，小端）
- Byte3~4 输出电压（0.1V/BIT）
- Byte5~6 输出电流（0.1A/BIT）
- Byte7 温度（1℃/BIT，-40 偏移）

但 `parse_status` 只解析 Byte0 故障字，**未解析 Byte1~7**；而模拟量查询 DCDC 又不应答 → 电压电流数据来源缺失。

**解决**：修改 [dcdc_protocol.cpp](file:///home/lingyun01/LINGYUN-CoPilot/src/airship_dcdc/src/dcdc_protocol.cpp) 的 `parse_status`，解析状态帧 Byte1~7 填充电压/电流/温度。新增单元测试 `ParseStatusWithAnalog`。

**验证**：状态帧解析 → 输入 395V / 输出 49.4V / 电流 4.8~5.2A / 温度 44℃，测试全部通过 ✅

---

### 问题 7：DCDC 输入欠压导致输出"通断"

**现象**：DCDC 输出状态反复通断，状态帧报 `0x05`（Bit0 输入欠压 + Bit2 输出开机），can0 在 ERROR-ACTIVE/ERROR-PASSIVE 间来回切换。

**根因**：DCDC 输入电压不足（低于 280V 最低工作电压）→ 欠压保护间歇触发 → DCDC 间歇掉线 → can0 发送无 ACK → ERROR-PASSIVE。

**处理**：输入电压恢复正常后（实测 395V），DCDC 稳定输出，状态帧变 `0x04`（无欠压），can0 保持 ERROR-ACTIVE。此为物理条件，非软件问题。

---

### 问题 8：笔记本解析脚本字段不全

**现象**：电脑端 `link_frame_parser.py` 只解析了部分字段：
- backup（12S）：缺 `pack_i`（电流）、`max_v/min_v/diff_v`、温度、`sys`
- dcdc：缺 `out_i`（输出电流）、`fault`

**解决**：提供完整解析脚本，覆盖 link_node 发送的全部设备与字段（bms/backup/mppt/dcdc/fc/lora），含单位标注。

---

### 问题 9：232 数传链路初期收不到数据

**现象**：电脑 USB 转 232 的 RX 灯不亮，收不到任何数据。

**排查**：
- 确认 link_node 软件层发送正常（wchar 稳定增长，~1100B/s = 5Hz）
- 确认 `/dev/ttyAMA0` 是微雪板 RS232 口（serial0 别名 = RP1 UART0）
- 确认 UART 未被 console 占用（cmdline.txt 无 console=serial0）
- 确认波特率 115200 8N1 匹配

**处理**：物理接线确认（232 线 TX/RX、微雪板 DB9 口）后链路打通。若再出现，优先检查 DB9 线序（交叉/直通）与 232 电平。

## 三、遗留问题与建议

| # | 事项 | 说明/建议 |
|---|------|----------|
| 1 | DCDC 模拟量查询不应答 | DCDC 固件可能不支持 `0x18D80047` 查询；已通过状态帧解析覆盖电压/电流/温度，无需依赖 |
| 2 | dcdc_hold 重启瞬间 TX 计数误报 | 重启后首条"TX 未增长"可能误报一次（last_tx 初始化时机），影响小，可选优化 |
| 3 | CAN 总线 ERROR-PASSIVE 风险 | 确认总线两端 120Ω 终端电阻、CANH/CANL 接线质量，避免 DCDC 掉线时错误累积 |
| 4 | LoRa 无线节点稳定性 | 温度曾全 0（瞬时离线），建议关注 LoRa 无线链路质量 |
