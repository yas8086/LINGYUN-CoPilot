## 一、树莓派系统看门狗（死机/假死硬件自愈）

### 目标
解决本机反复出现的"编译/内存打满导致系统假死、SSH 断连、只能手工断电复活"痛点，实现无人值守时死机自动硬件复位。

### 改动与部署
| 文件 | 作用 |
|------|------|
| `tools/rpi5_ubuntu2404_config.txt` | 基础区新增 `dtparam=watchdog=on`（启用 bcm2835-wdt 板载硬件看门狗） |
| `tools/systemd/90-airship-watchdog.conf` | systemd drop-in：`RuntimeWatchdogSec=20` / `RebootWatchdogSec=30`，装到 `/etc/systemd/system.conf.d/90-airship-watchdog.conf` |
| `tools/install_production.sh` | 新增 `install_watchdog()`，装配置文件 + `daemon-reload` |

### 部署生效
```bash
sudo bash tools/install_production.sh --watchdog
# 需重启系统以加载 config.txt 的 dtparam 与 system.conf.d
sudo reboot
```

### 验证
```bash
cat /proc/sys/kernel/watchdog              # 应输出 20(systemd 已接管喂狗)
cat /proc/device-tree/aliases/watchdog*    # 应有 watchdog 节点(硬件已使能)
journalctl -b | grep -i watch              # systemd 启动时喂狗日志
```

### 原理要点
- `dtparam=watchdog=on` 使能硬件看门狗；`systemd` 作为 **PID1** 周期性喂狗。
- PID1 卡死(如死循环/内存爆满、调度被拖死)超过 20s 未喂狗 → 硬件看门狗触发 → 整机硬件复位。
- `RebootWatchdogSec=30`：正常 reboot 若 30s 未完成也强制复位，防关机流程卡死。

## 二、rosbag 数据全量记录 + 每日清理

### 目标
飞行器系统必备：实机故障/复盘必须有**完整可回放数据**。原只有 `fc_monitor` 写 CSV（仅 fc 子集），无法还原全链路。

### 改动与部署
| 文件 | 作用 |
|------|------|
| `tools/airship-bag-record.service` | systemd：随 `airship-device-monitor` 启动，`ros2 bag record -a` 记录所有话题到 `/home/lingyun01/bags/<启动时间戳>/`；`Restart=always` |
| `tools/airship-bag-clean.service` + `airship-bag-clean.timer` | 每日一次（`OnCalendar=daily`）删 3 天前记录目录，防 TF 卡写满 |
| `tools/install_production.sh` | 新增 `install_bag_record()` |

### 部署与使用
```bash
sudo bash tools/install_production.sh --bag-record
# 查看记录文件
ros2 bag info /home/lingyun01/bags/<时间戳>
```

### 要点
- **`record -a` 会记录所有话题**（含高频 fc），TF 卡须留足空间；靠 3 天滚动清理兜底。
- 记录目录用启动时间戳命名，便于按实机时间定位事故现场。
- record 用户设为 `lingyun01`，依赖 install/setup.bash 存在（未构建则不记录，Restart 重试）。

### 坑
- systemd `ExecStart` 里需在 `ros2 bag record` 前 `source` ROS 与工作区环境（Type=simple + bash -c）。
- bag 目录若 TF 卡满会导致 record 崩溃，由 `Restart=always` 自动重拉（此时应关注磁盘告警）。

## 三、BMS 链路端到端集成测试（★★踩坑最多）

### 目标
把"节点注册 + 话题出数据 + 无数据离线兜底"这条用户最担心的链路固化为自动化测试，替代人工 `ros2 topic echo` 肉眼判断，并纳入 CI。

### 最终实现
- 新增 `tools/integration_test_bms.sh`：`online`（起 bms_node + sim_bms 发帧 → `ros2 topic echo --once /bms/status` 断言 `online: true`）/ `offline`（仅起 bms_node 不发帧 → 断言 `online: false` 离线兜底）。
- **CI**（`.github/workflows/ci.yml`）：`Test` 前自动建 vcan0（`modprobe vcan` + `ip link add vcan0`）；`Test` 后依次跑 `online`/`offline`。

### ★踩坑全记录（务必看，都是真金白银）

**坑 1：`set -u` 与 ROS 的 setup.bash 冲突**
- 现象：脚本 `source /opt/ros/jazzy/setup.bash` 时报 `AMENT_TRACE_SETUP_FILES: unbound variable`。
- 原因：Jazzy 的 `setup.bash` 内部访问未定义变量，而脚本开了 `set -u`。
- 解决：脚本用 `set -eo pipefail`（**去掉 -u**），未定义变量用 `${VAR:-default}` 显式兜底。

**坑 2：launch_testing 测试进程 import 不到 `airship_msgs`（PYTHONPATH 缺失）**
- 现象：`python3 -m launch_testing.launch_test` 报 `No module named 'airship_msgs'`，虽然 shell 已 `source install/setup.bash`。
- 原因：**ctest 直跑 launch_test 时，子进程没有继承 source 后的 PYTHONPATH**；工作区消息包的 python 绑定在 `install/airship_msgs/lib/python3.12/site-packages`，不在系统 site-packages。
- 尝试修复：在测试文件顶部用 `ament_index_python` 动态注入 site-packages 到 `sys.path` → **失败**：launch_test 进程连 `AMENT_PREFIX_PATH` 也没有，`get_package_prefix` 抛异常。
- 最终避开：改用 `os.path.dirname(__file__)` 定位仓库根拼 `install/...` 注入（自包含），但仍暴露坑 3。

**坑 3：launch_testing 测试方法 fixtures 注不进 + rclpy 与 launch 同进程冲突**
- 现象 a：测试方法签名带 `launch_context`/`proc_output` 报 `TypeError: missing 1 required positional argument`（fixture 未注入）。
- 现象 b：方法内 `rclpy.create_node()` 报 `RCLError: error creating node: error not set (rcl/node.c:252)` —— launch_testing 的 launch 与测试同进程，再 init rclpy 形成 context 冲突。
- 结论：**launch_testing 与本工程 rclpy 的 env/rcl-context 兼容矛盾多，调试成本极高**。
- 终局决策：**弃用 launch_testing**，改用独立脚本 + `ros2 topic echo` 独立 DDS 子进程断言（每个命令独立进程、天然隔离、无需 python 消息绑定/不用 rclpy），最稳。

**坑 4：`pkill -f "bms_node.*vcan0"` 杀掉了自己**
- 现象：诊断命令 `pkill -f ...` 后整个 shell 退出（exit -1），log 不存在。
- 原因：`pkill -f` 匹配**完整命令行**，诊断命令串里含 `bms_node` 和 `vcan0`，把自己匹配杀了。
- 教训：清理进程慎用 `pkill -f`；或先 `pgrep -af pattern` 看清 PID 再按 PID kill。

**坑 5：`timeout 10 ros2 topic echo --once` 无限卡死**
- 现象：脚本在线程无输出、命令长时间 running。
- 原因：GNU `timeout` 到期只发 **SIGTERM**；若 `ros2 topic echo`(DDS/cyclonedds) 不响应 SIGTERM，`timeout` **默认不 KILL**，无限等待。
- 解决：`timeout -k 5 10 cmd`（10s 到期后若未退再 5s 强制 SIGKILL）。

**坑 6：本机当前 RMW=cyclonedds + ROS_DOMAIN_ID=5，且生产 device-monitor 常驻**
- 现象：测试的 bms_node 报 `rmw_cyclonedds_cpp: failed to create domain` / `Failed to find a free participant index for domain 5`。
- 原因：**当前环境被设为 `RMW_IMPLEMENTATION=rmw_cyclonedds_cpp`、`ROS_DOMAIN_ID=5`**（本机无 fastrtps），且**生产中 device-monitor 的 14 个节点正占用 domain 5 的 participant**；测试再挤进同域导致 participant index 耗尽/创建失败。
- 解决：集成测试脚本内部 `export ROS_DOMAIN_ID=${INTEG_TEST_DOMAIN:-20}`，**隔离到独立域**，与生产互不干扰。

**坑 7：本机因生产常驻，DDS 集成操作极慢/卡，无法实时跑通**
- 现象：即便隔离域、加固 timeout，online 测试在本机仍长时间无输出。
- 原因：生产 mavros(60% CPU) + cyclonedds 发现机制拖慢 DDS 启动与发现；本机验证受环境严重干扰。
- 最终处理：**脚本面向 CI 干净环境运行**（CI 无生产干扰）；录音并在报告中如实标注"本机未实时跑通"。本机若想验，需先 `sudo systemctl stop airship-device-monitor` 释放资源，验完 `start` 恢复。

### 教训总结（针对未来写 ROS2 集成测试）
1. **不要在 launch_testing 测试进程里自己 rclpy.init + create_node**，容易 context 冲突；要么用 launch 标准 fixtures（但本版有问题），要么用独立进程断言。
2. **独立 DDS 子进程命令（ros2 topic echo）比进程内 python 订阅更稳**，特别是环境复杂时。
3. 测试环境变量（RMW / ROS_DOMAIN_ID / PYTHONPATH）会"坑"——脚本要显式设置/隔离，绝不假设继承。
4. 全部分类进程清理、timeout，都要防"自杀/挂起"。

## 四、核心监控话题显式 QoS

### 目标
为将来跨机/弱网打好基础，显式声明 QoS 语义，避免 reliable 在慢消费者上堆积队列、浪费内存并产生背压。

### 改动
- `airship_link/src/link_node.cpp`：7 个设备状态订阅 `rclcpp::QoS(10)` → `rclcpp::SensorDataQoS()`（best_effort + KeepLast(5)）。
- `airship_cloud/src/cloud_node.cpp`：同样 7 个订阅改 `SensorDataQoS()`。

### 为什么
- `link_node`/`cloud_node` 是"**只读最新一帧**"的纯数据中继：reliable + 深队列会堆积历史消息、费内存、产生背压。
- best_effort + KeepLast(5) 只保留最新，适合这类消费者。**生产端（bms 等）保持可靠发布**（保证有订阅者时每帧可达），best_effort 订阅可兼容 reliable 发布，两端 QoS 策略无需强一致到相同可靠性级别。

### 验证
- `colcon build --packages-select airship_link airship_cloud` 通过；单测通过，无回归。

### 注意
- 若后续某订阅方**要求不丢帧**（如 monitor/safety 的告警判据），应保持 reliable —— 本次**未改** monitor/safety 的订阅，仅改两个纯数据中继，符合此原则。
- `SensorDataQoS()` 来自 `rclcpp`（`#include <rclcpp/rclcpp.hpp>`），无需额外依赖。

## 六、坑速查表

| 坑 | 一句话解法 |
|----|-----------|
| `set -u` + ROS setup.bash → unbound | ROS 脚本用 `set -eo pipefail`，不要 `-u` |
| launch_test 进程缺 PYTHONPATH | 别依赖继承；用 __file__ 定位 install 注入，或干脆用独立子进程断言 |
| launch_test 里 rclpy init 冲突 | 别在 launch_testing 同进程里二次 init rclpy；改用 ros2 topic echo 独立子进程 |
| `pkill -f` 误杀自己 | 先 `pgrep -af pattern` 看 PID 再按 PID kill |
| `timeout` 无限等 | 加 `-k 秒`（到期后强制 SIGKILL） |
| RMW/domain 被污染、与生产冲突 | 脚本内显式 `export ROS_DOMAIN_ID=<隔离域>`，并明确 RMW |
| 本机有生产 DDS 常驻、验不过集成 | 面向 CI 干净环境；本机验前先 temp 停 device-monitor，验完恢复 |
