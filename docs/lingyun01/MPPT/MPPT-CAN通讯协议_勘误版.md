## 一、概述

本协议适用于我司 YQPV_SPC 系列和 YQPV_SMC 系列光伏控制器与上位机监控软件之间的通信，采用 CAN 总线形式。本协议可以实时读取控制器的运行数据、故障状态，以及设置控制器的相关数据。

---

## 二、物理接口

| 项目 | 参数 |
|------|------|
| 总线型式 | CAN2.0B |
| 波特率 | 250 Kbps |
| ID 类型 | 扩展帧（29 位） |
| 采样点 | 87.5% |
| 帧周期 | 小于 ±5% |
| 通信电缆 | 屏蔽双绞线 |
| 终端电阻 | **内部无**，若需要自行加装 120Ω-1/3W |

## 三、通讯格式（含勘误）

### 3.1 ID 扩展帧：29 位

一个 29 位扩展帧 ID 由 4 个域组成（5 位 + 8 位 + 8 位 + 8 位）：

| 位 | 含义 |
|----|------|
| 第 29~25 位 | 类型：只读数据为 `0x14`，配置数据为 `0x13` |
| 第 24~17 位 | 报文代码（code），范围 `0x00~0xFF` |
| 第 16~9 位 | 设备/目标地址 或 标志 `0xA1`（见下方发送/回应排布） |
| 第 8~1 位 | 标志 `0xA1` 或 设备/目标地址（见下方发送/回应排布） |

> 🔴 **勘误（原说明书此处位域定义与实际不符）**
>
> 原说明书写"第 16~9 位：目标地址固定 `0xA1`；第 8~1 位：发送此报文的源地址"。
> **该位域定义仅适用于从机回应帧，不适用于主机发送帧**，照抄会让人误以为发送帧末尾也是源地址。
> 实际上（实测确认）发送/回应两端的位域**是反过来的**，请以下方 3.2 为准。

### 3.2 读 / 写数据格式

**主机发送帧**（`0x14`/`0x13` + code + **设备地址** + `0xA1`）：

```
[0x14 或 0x13] [code] [设备地址] [0xA1]
 5位  8位   8位     8位
```

- 例：查 `0x01` 号 MPPT 的实时段 → `140301A1`（0x14 + 03 + 01 + A1）

**从机回应帧**（`0x14`/`0x13` + code + `0xA1` + 设备地址）：

```
[0x14 或 0x13] [code] [0xA1] [设备地址]
 5位  8位   8位     8位
```

- 例：`0x01` 号 MPPT 回应 → `1403A101`（0x14 + 03 + A1 + 01）

> 🔴 **勘误（发送/回应排布不对称，必须区分）**
>
> - **主机发送**：`0x14[code]设备地址 A1` → `140301A1`（设备地址在前，A1 在后）
> - **从机回应**：`0x14[code]A1 设备地址` → `1403A101`（A1 在前，设备地址在后）
>
> 说明书中"主机发送 `0x1401xxA1`，从机回应 `0x1401A1xx`"这句话正是这个意思——**字面是对的**（发送 xx 在 A1 前，回应 A1 在 xx 前），只是"上位区域定义表"里笼统写 `1403A1xx` 容易让人误以为发送也是 A1 在前。
> ✅ **代码已验证**：按 `140301A1` 发送 MPPT 才会响应；按对称排布 `1403A101` 发送则不响应。

- `0x00` 为广播地址，`0x01~0xF7` 为具体设备地址。

> ⚠️ **误区提示：`0x01` 是"哪台 MPPT"，不是"发送者自身"**
>
> 发送帧里的设备地址（如 `01`）是**目标从机（被查询的 MPPT）的 ID**，`A1` 才是协议标志。不要把 `01` 当成主机自己。

> 💡 **多台 MPPT 接入方法（你问的"再接一台改 02"）**
>
> 完全正确。若再并联一台同类 MPPT：
> 1. 在**新设备上**把其设备地址改成 `02`（通过配置命令 `0x13 04 A1 [设备地址]` 写设备地址，或设备面板设置）；
> 2. 在**代码里**把该 MPPT 的 `device_addr` 配成 `02`，并以 `140x02A1` 形式单独查询；
> 3. 接收端按设备地址区分响应（响应帧末尾 `02`）。
>
> 当前工程 `airship_params.yaml` 的 `mppt_node.device_addr: 1` —— **目前只支持 1 台 MPPT**。若要支持多台，需把查询逻辑扩展为按地址数组轮询（当前为单设备实现）。

### 3.3 数据帧格式

- 数据帧：8 字节，无效或预留位均置 0
- **只读数据格式**：主机发送**远程帧（RTR）**，从机回应**实时数据**
- **配置数据格式**：主机发送**数据帧**，从机回应配置数据；发送与回应数据相同表示相应字节配置成功

> ⚠️ **误区提示：主机"发送"不是数据帧，是 RTR 远程帧**
>
> 原文档说"只读数据格式：主机发送远程帧，从机回应实时数据"，意味着对**只读区段**，主机的查询帧应为 **RTR 远程帧（无数据负载）** 而非 8 字节数据帧。
> 但 ✅ 实测中（见上），用**带设备地址的 8 字节数据帧（数据全 0）**发送也能触发 MPPT 响应，说明该型号对"帧是否带数据"不敏感，只要**帧 ID 排布正确**即可。因此本工程实现采用 8 字节数据帧发送。

### 3.4 数据编码

- **数据转换**：实际数值 = 总线上传送的数值 × 分辨率 + 偏移量
- 字节发送顺序：字节0、字节1、……、字节7
- 位发送顺序：位7、位6、……位0
- **数据编码**：采用 Intel 编码格式（低字节在前，高字节在后 / little-endian）

## 六、本工程对接备注（实测结论）

1. **发送帧排布**：主机发送用 `0x14|code|设备地址|0xA1`（如 `140301A1`），从机回应用 `0x14|code|A1|设备地址`（如 `1403A101`）。两者**不对称**，发送与接收排布不同。
2. **设备地址**：用具体设备地址（本项目 MPPT=1），避免用广播 `0x00` 发送（实测广播可能不应答）。
3. **查询帧类型**：本项目用 8 字节数据帧（数据全 0）发送只读查询；实测可触发响应（对 RTR 不敏感）。
4. **波特率必须 250K**：与 micro雪板 can0（250k）一致。
